1. Введение

Актуальность

Малые производства РФ ведут оперативный учёт ТМЦ на бумаге: данные попадают в 1С с задержкой 1–3 дня, закупки планируются «по опыту». Следствие — дефицит сырья, простои линий (до 50 000 ₽/час) и замороженные оборотные средства. Коробочные WMS (1C:WMS, Axelot, SAP EWM) недоступны SME: внедрение от 5 млн ₽ и месяцы работ.

Цель

Разработать и внедрить интеллектуальную WMS с ИИ-прогнозом закупок: время «сигнал → заказ» с 3 дней до 30 минут; 0 простоев из-за дефицита; запасы −15–20%; 100% аудит-след.

Обзор практик и методология

Практики: облачные SaaS (МойСклад — розница, не производство), serverless-платформы, ИИ-ассистенты в разработке (code generation, документация, отладка), Agile/Scrum для ИИ-проектов. Методология: Design Thinking (эмпатия к работнику цеха), итеративное прототипирование, human-in-the-loop для критических решений («ИИ рекомендует — человек решает»).

2. Теория предмета в прикладном использовании

WMS-системы

Warehouse Management System автоматизирует приёмку, хранение, перемещение и отгрузку ТМЦ: учёт остатков в реальном времени, партии и сроки, интеграция с ERP, аналитика спроса. В прикладном контуре «Ремеры» WMS не подменяет 1С, а дополняет её оперативным контуром движений с двусторонним CSV-обменом.

Прогнозирование временных рядов

  • скользящее среднее — стабильный спрос;
  • экспоненциальное сглаживание (Holt–Winters) — тренд и сезонность;
  • градиентный бустинг (XGBoost/CatBoost) — нелинейности и внешние факторы.

В MVP применён детерминированный базис: точка заказа = запас < норма × 7 дней; рекомендация = норма × 14 − запас. ML-надстройка (бустинг, 14 дней) — Sprint 3/4: сначала накоплен журнал движений (источник обучающей выборки).

Human-in-the-loop

Каждая рекомендация ИИ и каждый рапорт проходят утверждение человеком (директор). Обоснование: цена ошибки автопроводки на производстве — остановка линии; HITL даёт контроль, доверие пользователей и размеченные данные для дообучения модели.

Agile в ИИ-проектах

Waterfall неприменим из-за неопределённости качества моделей и требований. Scrum с двухнедельными спринтами: бэклог (AGILE.md), канбан (Яндекс-таблицы), демо заказчику каждый спринт, KPI «базлайн AS-IS → цель TO-BE».

Принцип Data-firstСначала журнал движений и справочник — потом модели и автоматизация.
Security by defaulttry-catch и fallback на каждом узле; валидация всех входов.
Zero-downtimeДеградация хранилища не роняет приём рапортов (in-memory + ретрай).

6. MVP и сценарии использования

План создания MVP (7 недель)

Нед. 1–2 ядро (авторизация, рапорты, проводки) → нед. 3 CSV ↔ 1С → нед. 4 аналитика точки заказа → нед. 5 руководство → нед. 6 тесты → нед. 7 пилот. MVP в бою с 07.09.2026.

Матрица интеграции в бизнес-процессы

ПроцессAS-ISTO-BE
Расход сырьябумага → звонок → бухгалтер → 1С (1–3 дня)телефон → очередь → кнопка «Провести» (15 сек)
Приход от поставщиканакладная → бухгалтер (1 день)CSV-импорт с валидацией (5 мин)
Сверка с 1Сручная выгрузка (2 часа)CSV-экспорт с BOM (5 мин)
Закупки«по опыту»точка заказа: запас < 7 дней нормы + рекомендация
Рис. 3 — Поток TO-BE: от движения материала до заявки поставщику

Сценарий использования: рапорт работника (основной поток)

  1. Работник открывает chat.html на смартфоне, вводит PIN → роль «worker» (/api/auth).
  2. Кнопка «Расход» → конструктор команд: ввод «капрон» → подсказка кода PA-F из 108 позиций.
  3. Количество 5 → валидация (код из справочника; 0 < qty ≤ 1 000 000).
  4. Порог аномалии: 5 ≤ норма×10 (150×10) → подтверждение не требуется.
  5. /api/chat кладёт рапорт в очередь pending; работник видит «Принято: 5 × PA-F».
  6. Директор жмёт «Провести» → /api/approve: идемпотентность, stock −= 5, запись в movements с автором и утвердителем.

Альтернативные потоки: аномальное qty (> норма×10) → запрос подтверждения «!»; отклонение директором → удаление из pending без проводки; бухгалтер → только чтение и CSV-экспорт.

7. Протоколы кибербезопасности

Аутентификация и роли

MVP: PIN (4 цифры) из переменных окружения Amvera (секреты); проверка PIN и роли на каждом из 7 эндпоинтов. Роли: работник (запись рапортов), директор (проводки + чтение), бухгалтер (только чтение + экспорт). Sprint 3: JWT с TTL 8 ч, refresh, blacklist отзыва.

Меры по классам угроз

УгрозаМитигация
Подбор PIN (brute force)rate limiting на уровне платформы; PIN только в env, не в коде и логах
XSSэкранирование пользовательского ввода при рендеринге чата и журнала
CSRF / подмена запросапроверка Origin, SameSite для сессий (с JWT — заголовок Authorization)
DoS / переполнениелимит тела запроса 5 МБ, импорт ≤ 2000 строк, messages ≤ 500
MitMHTTPS с валидным сертификатом (Terminator TLS на Amvera)
Потеря данныхpersistence mount /data, идемпотентность проводок, защита от отрицательных остатков
Двойная проводка (двойной клик)идемпотентность по id/sign рапорта

Аудит и этика

  • аудит-след 100%: автор, утвердитель, метка времени, id по каждой проводке;
  • 152-ФЗ: данные хранятся на территории РФ (Amvera);
  • этика ИИ: human-in-the-loop — ИИ не проводит операции самостоятельно; рекомендации объяснимы (формула точки заказа прозрачна);
  • bias/privacy: персональные данные работников не собираются (имя + роль), обучение ML только на обезличенных движениях ТМЦ.

9. База данных и источники данных

Структура состояния (/data/wms2/state.json)

{
  "version": 1,
  "stock":     { "PA-F": 1500, "PES-F": 800, ... },        // остатки: код → qty
  "pending":   [ { id, author, ts, op, code, qty } ],       // очередь рапортов
  "movements": [ { id, author, approver, ts, op, code, qty } ], // журнал проводок
  "messages":  [ { id, ts, role, text } ]                   // чат, последние 500
}
ПолеТипНазначение
versionintверсия схемы для миграций
stockobjectоперативные остатки ТМЦ
pendingarrayрапорты, ожидающие утверждения (human-in-the-loop)
movementsarrayаудит-след: автор + утвердитель + время
messagesarrayистория чата (ограничение 500 записей)

Источники данных

ИсточникФорматЧастотаНазначение
Рапорты работниковчат-командыреальное времядвижения ТМЦ
Накладные поставщиковCSVпо поставкеприход
Выгрузка 1СCSVежедневносверка остатков
Справочник номенклатурыJS-константа (core.js)статика108 позиций + суточные нормы

Валидация и ограничения

  • коды — только из справочника NOMENCLATURE; qty: 0 < qty ≤ 1 000 000;
  • защита от отрицательных остатков: проводка отклоняется при stock < qty;
  • импорт ≤ 2000 строк; экспорт CSV с BOM \uFEFF для Excel;
  • нормализация при переходе на PostgreSQL (Sprint 3/4): items, stock, movements, users + индексы по item_id, ts, op.

Оценка по критериям оптимальности

  • Time-to-market: MVP за 7 недель вместо отраслевых 6–12 месяцев — отлично;
  • Стоимость: 0 ₽ инвестиций — отлично;
  • Качество: покрыты все критические процессы (рапорт, проводка, 1С, аналитика) — хорошо;
  • Масштабируемость: архитектура допускает рост после рефакторинга БД — удовлетворительно (осознанный компромисс MVP);
  • Принятие пользователями: заказчик и пилот-пользователь вовлечены с первого спринта — хорошо.

Итог

Стратегия «low-code инфраструктура + ИИ-ассистент + Agile + human-in-the-loop» оптимальна для стадии MVP: минимальный бюджет и срок при полном аудит-следе и готовности к масштабированию. Технический долг (PIN, JSON-хранилище) зафиксирован в дорожной карте и не является скрытым. Следующий шаг — двухнедельный пилот на производстве: его метрики (время рапорта, доля рапортов через WMS, «сигнал → заказ») определят переход к тиражированию.
